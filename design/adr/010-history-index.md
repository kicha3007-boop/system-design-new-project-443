# Составной индекс для истории поездок пассажира

Автор: Kichigin Sergey. Замеры: [reports/baseline.md](../../reports/baseline.md) до решения и [reports/after-index.md](../../reports/after-index.md) после него. Требование, которое проверяется, записано в [design.md](../../design.md#требования).

## Контекст и проблема

История пассажира `GET /passengers/{id}/trips` выполняет один запрос:

```sql
SELECT id, passenger_id, driver_id, status, price,
       pickup_address, destination_address, created_at
FROM trips
WHERE passenger_id = $1
ORDER BY created_at DESC
LIMIT 20;
```

Требование из _design.md_: p95 истории меньше 50 мс на 2 000 000 поездок при доле ошибок не больше 0.1 %.

Базовый замер [reports/baseline.md](../../reports/baseline.md) (профиль `mixed`: 5 созданий, 20 чтений состояния, 5 чтений истории в секунду, 30 с после прогрева; 2 000 000 поездок, 10 000 пассажиров):

- p95 истории 1103.5 мс, медиана 148.3 мс, максимум 2102.9 мс, то есть цель нарушена в 22 раза;
- ошибок 0 из 954, `dropped_iterations` 0, поэтому генератор подал полную частоту и числа говорят о сервисе;
- `EXPLAIN (ANALYZE, BUFFERS)`: `Parallel Seq Scan on trips`, прочитано 2 000 000 строк и 54 223 страницы (около 424 МБ), чтобы вернуть 20 строк, затем сортировка top-N; 103–113 мс в одиночку;
- в метриках приложения ожидание пула p95 0 мс, время SQL p95 122–230 мс: время уходит в базу.

В таблице `trips` есть только первичный ключ по `id`. Полный просмотр растёт линейно с таблицей: при среднем потоке 73 млн поездок в год запрос станет в десятки раз медленнее, поэтому оставлять так нельзя.

## Какие варианты сравнивали

| Вариант | Что даёт этому запросу | Почему выбран или отвергнут |
| --- | --- | --- |
| 1. Оставить схему как есть | ничего, полный просмотр 2 млн строк на каждое открытие истории | Отвергнут: p95 1103.5 мс при цели 50 мс уже на 2 млн строк, время растёт с таблицей. Наращивать ресурсы базы под полный просмотр дороже, чем индекс, и не убирает рост |
| 2. Индекс только по `passenger_id` | база находит 200 поездок пассажира, но в произвольном порядке, читает все 200 строк таблицы и сортирует их ради 20 | Отвергнут: работа растёт с числом поездок пассажира, а не с размером ответа. У частого пассажира за годы набираются тысячи поездок, и каждое открытие истории читает и сортирует их все. Объём индекса почти тот же, что у составного, потому что `created_at` добавляет к записи 8 байт |
| 3. Составной индекс `(passenger_id, created_at DESC)` | спуск по дереву к пассажиру, записи уже в порядке `created_at DESC`, чтение останавливается на 20-й; сортировки нет | **Выбран**: порядок полей повторяет запрос, первое поле совпадает с условием `WHERE passenger_id = $1`, второе с `ORDER BY created_at DESC`. Работа запроса ограничена `LIMIT 20` и не зависит ни от размера таблицы, ни от длины истории пассажира |

Другие пути, например покрывающий индекс со всеми колонками ответа (`INCLUDE`) или отдельная копия базы для истории, не рассматривались подробно: они дороже по объёму или по устройству, а замер после варианта 3 уже укладывается в цель с запасом.

## Решение

Добавить индекс `trips_passenger_created_idx ON trips (passenger_id, created_at DESC)` отдельной миграцией [db/migrations/003-history-index.sql](../../db/migrations/003-history-index.sql). Миграция использует `CREATE INDEX IF NOT EXISTS`, поэтому `make migrate` можно запускать повторно без ошибки: второй прогон пропускает индекс. Код приложения и запрос не меняются.

## Последствия

Хорошее:

- чтение истории: план становится `Index Scan using trips_passenger_created_idx`, 20 строк и 23 страницы вместо 2 000 000 строк и 54 223 страниц, сортировки нет;
- база перестаёт тратить ядра и кэш на полные просмотры, это освобождает ресурсы для остальных потоков, p95 всех запросов прогона упал с 194.8 до 10.3 мс;
- время истории теперь зависит от размера ответа, а не от размера таблицы.

Плохое, то есть цена:

- хранение: на 2 млн поездок индекс занимает 60 МБ при построении по готовой таблице и 78 МБ после заливки строк при уже существующем индексе, это 14–18 % к таблице в 423 МБ. При среднем потоке 73 млн поездок в год это около 2.3–3 ГБ индекса в год, считая 32–41 байт на строку из того же замера;
- запись: каждая вставка поездки обновляет на один B-tree больше. На стенде заливка 2 млн строк с индексом заняла 134.9 с против 127.5 с без него, +6 %; единичная вставка в профиле `mixed` в среднем 0.38 мс, и вклад индекса в ней в пределах разброса. Заметной цена станет при массовых загрузках и при пиковом создании поездок, если в таблицу добавят ещё индексы;
- изменения `passenger_id` и `created_at` обновляют индекс, но приложение этих полей после вставки не меняет; смена статуса поездки индекс не задевает;
- `CREATE INDEX` без `CONCURRENTLY` блокирует запись в `trips` на время построения: на 2 млн строк около 1.2 с, на городском объёме это минуты, поэтому там индекс нужно строить `CONCURRENTLY` в отдельной миграции вне транзакции.

## Подтверждение

Измерено, а не предположено ([reports/after-index.md](../../reports/after-index.md), тот же профиль, те же 2 000 000 поездок после повторной детерминированной заливки):

| Показатель | baseline | after-index |
| --- | --- | --- |
| p95 истории | 1103.5 мс | 7.9 мс |
| строк таблицы на запрос | 2 000 000 | 20 |
| страниц на запрос | 54 223 | 23 |
| доля ошибок | 0.00 % | 0.00 % |
| `dropped_iterations` | 0 | 0 |

Цель p95 < 50 мс выполнена. Предположением остаётся поведение на городском объёме и на отдельных серверах: стенд проверил 2 млн строк на одной машине.

Постоянная проверка: автотест плана (`EXPLAIN` истории содержит `Index Scan`) и повторный `make load PROFILE=mixed NAME=after-index` после изменений запроса или схемы `trips`.

Условие отката: индекс удаляется новой миграцией (`DROP INDEX CONCURRENTLY IF EXISTS trips_passenger_created_idx`), если выполняется одно из двух:

- план истории перестал использовать индекс, например после изменения запроса, и индекс только платит за запись и место;
- повторный замер тем же профилем показывает, что время создания поездки выросло больше чем на 20 % относительно прогона без индекса, и запись важнее истории.

Пока история читается этим запросом, откат вернёт p95 истории к значениям базового замера, поэтому без замены индекса другим решением его не откатывают.
